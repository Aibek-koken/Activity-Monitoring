## November 18 UX and performance pass

- Notifications retain read and past items until an explicit delete. Their dialog shows the full message and context, with a separate navigation action. The bell count covers current unread items, and bulk read covers all pages.
- Translators give a reason to request an existing daily-record edit. The project's Project Manager may approve or decline; an approval permits one edit only while the activity remains active. The server enforces the rule.
- Final submission opens a simple receipt with navigation choices; correction-required work continues to show its correction screen. The editor's saved checking estimate appears to the translator and refreshes while the activity is under checking.
- The Chief Editor selects a project before viewing its versions, with project search and version filters. Local demo seeding adds 10 projects, 20 Maya activities, Sofia Bianchi assignments, and PDF sample marks placed over text. Existing user-created or older demo marks are not rewritten.
- Correction decisions can record page numbers and ranges, deriving the count. Mark deletion now confirms before sending a `204` response, with an optional browser preference to skip future prompts. Generated PDF highlights are translucent.
- The translator list batches assignment and progress reads, and the review queue batches annotation counts. These remove per-row database queries; latency has not yet been benchmarked against a production-sized database.

## Known Bugs And Risks

- The domain now presents translated volume as pages in the product UI. Existing numeric values were not converted; they keep their stored precision and are treated as pages going forward. The ERD still describes the column generically as `TranslatedVolume`.
- Team coordination gap: responsible and assisting translators can see the shared weekly remaining estimate but only their own daily records. Assignments do not identify a file, page range, segment, or other exclusive work scope, so the current model cannot detect or prevent two translators from reporting work on the same source content. A future team-workflow increment should add scoped work packages and shared activity progress before treating summed daily volume as unique translated output.
- Production settings still need a real JWT secret, secure cookies over HTTPS, narrowed CORS origins, and demo seeding disabled.
- Review bytes live in a private filesystem while metadata lives in PostgreSQL. Production backup/restore must keep them consistent; there is no object-storage adapter, retention/deletion workflow, or orphan-reconciliation job.
- Chief Editor workload compares the whole open queue with a manually saved weekly availability. It has no calendar due dates, automatic capacity inference, or per-day distribution.
- Chief Editors can page only the open queue. After a decision, the UI returns to the project's open queue with a confirmation; a closed review stays readable at its direct detail URL, but there is no browsable Chief Editor closed-history screen. Responsible translators have full per-activity cycle history.
- In-app marks and generated annotated PDFs are PDF-only. DOCX files remain download-only; there is no DOCX preview, direct PDF text editing, collaborative review, or diff.
- The PDF text layer is an in-browser approximation for selection. Scanned pages have no text layer, so reviewers use the box tool; this is intentional and explained in the UI.
- `ChiefEditorAssignmentService` limits sequential normal assignments to one responsible project and V8 cleans existing duplicates; non-production demo seeding bypasses this quota for Sofia only. There is no editor-scoped database uniqueness guard or concurrent-assignment test yet. The manager staffing API replaces a responsible translator but does not enforce the documented separate translator limits of 5 active responsible and 10 active assisting assignments.
- The teammate's original V5 staffing migration was renumbered and adapted as V9 because Sprint 4 had already applied V5–V8 locally. A database that applied the teammate's different V5 before this merge has divergent Flyway history and needs a reviewed one-time reconciliation before running the merged application.
- The original six-sprint overview and master user-story file referenced in `PROJECT_CONTEXT.md` are not present in this workspace. Sprint 3's scope was cross-checked against available design sources; reminder schedule and estimate ownership are recorded project decisions.

## Decisions Made

- Keep the backend as a layered modular monolith.
- Use JWT in an `HttpOnly` cookie plus CSRF protection.
- Do not expose a public self-registration flow; users are expected to be provisioned outside the public UI.
- Keep the UI light, restrained, and operational.
