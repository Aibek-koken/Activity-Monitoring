# Sprint 5 — единое задание для команды (US-24–US-35)

Дата подготовки: 2026-11-12; актуализировано: 2026-11-19. Статус: **план; Sprint 5 не реализован**.

Этот файл можно передать каждому из четырёх исполнителей и их ИИ. Каждый выбирает **один кейс** из таблицы ниже и реализует только его. Пятый участник — интегратор: принимает ветки, разрешает конфликты, запускает общую проверку. Это рабочая детализация черновых QA-критериев из сообщения команды, а не утверждение, что все приведённые ниже продуктовые решения уже согласованы с заказчиком.

## 2. Общий старт и правила параллельной работы

1. **Интегратор сначала фиксирует и проверяет Sprint 4.** На 2026-11-19 его код интегрирован в рабочее дерево `main`, но остаётся незакоммиченным. Нельзя начинать Sprint 5 от текущего `HEAD`: нужен единый проверенный коммит, включающий применённые миграции до V8. Интегратор сохраняет чужие текущие изменения; не выполняет `reset --hard`/`clean` на общем дереве.
2. После фиксации Sprint 4 все берут **один и тот же commit SHA**. Работа — в отдельных Git-ветках и отдельных worktree/клонах. Исполнитель A первым выпускает небольшой **контрактный PR**: V9 и модели/DTO/маршруты, необходимые B–D. Интегратор его быстро объединяет. Затем все четыре кейса могут выполняться параллельно: A продолжает собственные экраны и тесты, B–D начинают от объединённого контракта A. До этого B–D могут проектировать и писать независимые тесты/компоненты, но не создавать альтернативные схемы и API.
3. Контрактный PR A фиксирует названия полей, DTO, URL, роли, статусы и базовую навигацию. Изменение контракта после объединения — отдельное короткое сообщение всей команде и согласованное изменение, а не локальная догадка ИИ.
4. Зарезервировать новые миграции после уже применённой V8: **A — V9**, **B — V10**, **D — V11**, **C — V12**. Номера не переиспользовать; применённые V1–V8 (включая V5.1/V5.2) не менять. Слияние в порядке A → B → D → C. Каждая ветка использует свою одноразовую тестовую БД: если более позднюю миграцию применить до добавления предыдущей в той же постоянной БД, Flyway может отклонить последующее добавление более ранней версии.
5. Общие точки интеграции `frontend/src/App.tsx`, `frontend/src/lib/api.ts`, `frontend/src/styles.css`, `backend/.../config/SecurityConfig.java`, `docs/API.md`, `docs/ARCHITECTURE.md`, `docs/DESIGN.md` редактирует **A в контрактном PR** или **интегратор при слиянии**. Остальные добавляют свои страницы, компоненты, стили через существующие semantic CSS variables, DTO, controllers/services/repositories и feature API в собственных файлах. Если без общего файла нельзя, исполнитель пишет точный патч/инструкцию в PR, а интегратор применяет его после слияния. Не делать широких форматирований существующих файлов.
6. Каждый исполнитель обновляет `docs/STATE.md` в своей ветке в конце сессии, как требует `AGENTS.md`. Интегратор при слиянии сохраняет записи всех четырёх, а не выбирает одну версию файла. У каждого PR есть короткое описание контрактов, миграции, сценариев QA и реально запущенных проверок.
7. В существующем проекте auth — JWT в `HttpOnly` cookie и CSRF; роли защищаются сервером. Контроллеры не обращаются к репозиториям напрямую. Новый код следует слоям controller → service → repository/model/DTO. UI читает `docs/DESIGN.md`, использует существующие CSS-переменные и `$frontend-design`; бизнес-правила остаются в backend.

### Согласованный контракт, который закрепляет A

- Менеджер видит только проекты, где `project_manager_id` равен его authenticated user id. Любой manager endpoint повторно проверяет эту принадлежность; угаданный ID чужого проекта/активности не раскрывает данные.
- Базовый префикс API: `/api/v1/project-manager`; React-маршрут: `/project-manager`. Страница проекта: `/project-manager/projects/:projectId`; активности: `/project-manager/projects/:projectId/activities/:activityId`.
- `projects` уже содержит название и владельца, но **не содержит статус**. Для US-25 статус проекта выводится из активностей: `NO_ACTIVITIES`, `ACTIVE` (есть хотя бы одна незавершённая), `COMPLETED` (есть активности, все `COMPLETED`). Отображаемое название статуса можно локализовать в UI. Не вводить произвольный статус проекта без отдельного решения.
- Между US-26 и US-27 активность может существовать без переводчика. A добавляет `DRAFT`/`UNASSIGNED` (выбрать одно имя и зафиксировать в контракте) в enum и CHECK через V9; назначение переводчика переводит её в существующий `ASSIGNED`. Проверить существующие фильтры и переходы Sprint 2–4 на новый статус. Для новых активностей A добавляет плановые `startDate` и `dueDate` (nullable для старых строк, обязательны в новом create API), чтобы B мог честно показывать календарную доступность и конфликт. Даты валидируются на сервере (`startDate <= dueDate`).
- Общий формат ошибок остаётся существующим: `400` валидация, `401` без входа, `403` чужая роль/запрещённая операция, `404` объект вне области менеджера, `409` конфликт состояния/уникальности. Все мутации требуют CSRF.
- A добавляет в общем frontend API слой экспортируемые безопасные JSON GET/POST/PUT/PATCH helpers с `credentials: include` и CSRF для мутаций. B–D используют их в собственных feature-модулях; JWT нигде не хранится в browser storage.

## 3. Полный перечень историй и готовые задания

### Кейс A — US-24, US-25, US-26, US-27

**Что сделать**

- **US-24 Create Project (4):** вошедший Project Manager создаёт проект с непустым уникальным именем; сервер устанавливает владельца из сессии и дату сам. После сохранения проект виден в его списке.
- **US-25 View Projects (3):** список только своих проектов с названием, датой и вычисленным текущим статусом. Пустое состояние и загрузка/ошибка должны быть понятны пользователю; чужие проекты не видны даже по прямому URL.
- **US-26 Create Activity (4):** создать внутри своего проекта активность с уникальным номером, названием и плановым интервалом. Начальное состояние — выбранный в контракте draft/unassigned. Пустые и неверные поля отклоняет backend. Новый объект появляется в проекте.
- **US-27 Assign Responsible Translator (4):** выбрать пользователя с ролью `TRANSLATOR` и назначить его единственным ответственным на активность без ответственного. Сохранить в `activity_translators`, перевести активность в `ASSIGNED`. Не перезаписывать уже существующее назначение; последующая замена — кейс B. При назначении считать **активные** ответственные активности отдельно от ассистирующих: лимит 5 ответственных, 10 ассистирующих из ранее зафиксированного требования. Считать закрытые/завершённые вне лимита; точный набор активных статусов зафиксировать в контракте и тестах.

**Граница кода:** новые `ProjectManagerProject*` и `ProjectManagerActivity*` controller/service/DTO/repository-запросы, V9, менеджерская оболочка/список/деталь/форма, собственные тесты. A владеет первичным изменением `ActivityStatus`, `Activity`, общих маршрутов и security matcher. Не реализовывать B–D.

**API-контракт для интеграции:** `GET/POST /project-manager/projects`, `GET /project-manager/projects/{projectId}`, `GET/POST /project-manager/projects/{projectId}/activities`, `GET /project-manager/projects/{projectId}/activities/{activityId}`, `POST /project-manager/projects/{projectId}/activities/{activityId}/responsible-translator`. DTO активности содержит `id`, `activityNumber`, `activityName`, `status`, `startDate`, `dueDate`, `responsibleTranslator` (nullable). DTO проекта содержит вычисленный `status`. Список доступных переводчиков для формы — отдельный manager-scoped read endpoint, возвращающий безопасные `id/fullName`, без паролей/email при отсутствии нужды.

**QA:** создать проект → увидеть в списке → создать активность → назначить переводчика → увидеть сохранённое имя; чужой менеджер не читает/не меняет проект; неправильная роль, дубликат номера/имени, неверные даты и шестое активное ответственное назначение отклоняются; существующий Sprint 3–4 поток не сломан.

### Кейс B — US-28, US-29, US-30

**Что сделать**

- **US-28 View Translator Availability (5):** отдельные вручную управляемые интервалы доступности переводчика (даты `from/to`, статус available/unavailable и необязательная заметка). Manager видит эти интервалы и пересечения с плановым интервалом активности. Если данных нет, UI/API говорят **«неизвестно»**, а не «свободен». Конфликт показывать вместе с основанием; отсутствие конфликта не гарантирует свободное время вне внесённых данных.
- **US-29 View Translator Workload (5):** список других активных назначений выбранного переводчика с ролью в каждой активности, названием проекта, статусом и плановыми датами. Не раскрывать лишние данные чужого проекта: если назначение в проекте другого менеджера, для оценки нагрузки можно показать ограниченное описание без ссылок/деталей, согласно контракту доступа. Отдельно показывать количество ответственных/ассистирующих и лимиты 5/10.
- **US-30 Replace Translator (5):** менеджер заменяет ответственного в своей активности. Проверить роль нового пользователя, его активную квоту и доступность/конфликт на нужные даты. Выполнить смену атомарно под блокировкой активности, сохранить историю прежнего/нового ответственного, не уничтожать старые рабочие записи и review history. Если активность уже в проверке или завершена, замена требует отдельного будущего правила и сейчас возвращает `409`; разрешённые статусы — `ASSIGNED`/`IN_PROGRESS`. Для `IN_PROGRESS` показать подтверждение в UI. Старый ответственный теряет доступ к редактированию после замены; исторические записи сохраняют автора.

**Граница кода:** V10 (календарная доступность и история замен), `ManagerStaffing*` controller/service/DTO/repository, отдельные staffing-компоненты/страницы/тесты. Использовать API/модели A. Не менять `ProjectManagerProject*`, `ActivityStatus`, общий `App.tsx`, Sprint 4 review service. Если сохранение прежних записей требует коррекции сервисов Sprint 2–3, оформить маленький изолированный патч и явно выделить его в PR.

**API-контракт:** `GET/POST /project-manager/translators/{translatorId}/availability`, `GET /project-manager/translators/{translatorId}/workload?activityId=...`, `POST /project-manager/projects/{projectId}/activities/{activityId}/replace-responsible` с `newTranslatorId` и опциональным пояснением. Сервер сам вычисляет пересечения и квоты; UI не решает, можно ли заменить.

**QA:** доступный/недоступный/неизвестный интервалы; нагрузка содержит другие активные задания; замена сохраняется, прошлые записи не меняются, старый пользователь не может продолжать работу; конкурентные запросы не создают двух ответственных; чужой менеджер и редактор не могут заменить; активный лимит соблюдён.

### Кейс C — US-31, US-35

**Что сделать**

- **US-31 Assign Additional Chief Editor (5):** менеджер видит нагрузку Chief Editors из Sprint 4 (число открытых reviews, известные часы и количество reviews без оценки). Он добавляет редактора с ролью `CHIEF_EDITOR` как **дополнительного** в свой проект, не снимая ответственного. Один Chief Editor ответственен только за один проект; остальные назначения — assisting (`is_responsible = false`). Использовать существующий `ChiefEditorAssignmentService` с лимитом `MAX_RESPONSIBLE_PROJECTS = 1`, а не создавать `ProjectChiefEditor` напрямую. Чтобы поддержка проверки действительно работала, менеджер может передать выбранный **открытый** Review дополнительному редактору. Делать передачу атомарно, с записью кто/когда/от кого/кому; закрытые Reviews неизменны. После передачи право просмотра, скачивания файла и решения получает новый назначенный редактор по правилам Sprint 4. Проверить отсутствие гонки с закрытием Review; старый редактор не должен продолжать решать переданный Review.
- **US-35 Monitor Translator Performance (6):** текущий Sprint 4 хранит текст `mistakes_notes`, но не достоверное число ошибок. Добавить структурированное `mistakeCount` (неотрицательное целое) в решение Chief Editor и сохранение Review; старые решения остаются с `null` = нет данных. Для скорости использовать фактические `work_records.translated_volume / work_hours` только при положительных часах; строки без часов не считать «медленной работой». Менеджеру показать только данные активностей **своих проектов**: по каждому переводчику наблюдаемый период, число проверенных работ, сумму известных ошибок, объём, часы и скорость; флаг «много ошибок»/«низкий темп» вычисляет backend по **явным конфигурируемым порогам** и минимальной выборке. Рабочий стартовый порог ошибок: минимум 3 проверенных Review с заполненным `mistakeCount`, суммарно 5 или больше ошибок. Для темпа из-за неизвестной единицы объёма использовать сравнение с медианой других переводчиков того же проекта и периода: минимум 5 часов у оцениваемого, минимум 2 сравнимых коллег с 5 часами каждый; флаг, если темп ниже половины медианы. При отсутствии сравнения — «недостаточно данных». В UI дать объяснение порога и данных, без негативного флага при недостатке данных. Не выводить субъективный рейтинг из свободного текста.

**Граница кода:** V12 (mistake count, audit передачи), `ManagerEditor*`/`ManagerPerformance*` controller/service/DTO/repository и свои UI/тесты. C один владеет точечными изменениями Sprint 4 `Review`, review decision DTO/service и формы Chief Editor для ввода количества ошибок. Не редактировать файлы A/B/D; изменения общих маршрутов передать интегратору патчем.

**API-контракт:** `GET/POST /project-manager/projects/{projectId}/additional-editors`, `GET /project-manager/chief-editors/workload`, `POST /project-manager/projects/{projectId}/reviews/{reviewId}/reassign-editor`, `GET /project-manager/translators/performance?from=...&to=...`. Решение Review включает nullable `mistakeCount`; API отдаёт вместе с показателями статус достоверности данных и применённые пороги.

**QA:** дополнительный редактор из другого проекта добавлен, ответственный остался; открытый Review после передачи доступен/решается только новым редактором; закрытый Review не передаётся; тестовые ошибки/медленный темп дают объяснимый флаг, нормальные и неполные данные не дают ложный; legacy reviews с `null` работают; соседний менеджер не видит персональные показатели своих чужих проектов.

### Кейс D — US-32, US-33, US-34

**Что сделать**

- **US-32 View Activity Progress (5):** в детали активности менеджер видит сумму фактически записанных часов (только известные часы), суммарный объём из дневных записей **всех** назначенных переводчиков и последнее оставшееся значение из weekly estimates. Подписать, что суммарный объём — отчётные записи, а не гарантированно уникальный текст: в текущей модели нет разграничения фрагментов. Отсутствующий остаток/часы показывать как «нет данных», не как ноль.
- **US-33 View Estimated Total Work (5):** оценка полного объёма на момент weekly estimate = накопленный объём на тот момент + тогдашний остаток. Для честного исторического сравнения при сохранении/обновлении weekly estimate хранить snapshot накопленного объёма; старые строки без snapshot помечать как legacy/«историческая оценка недоступна», а не пересчитывать из нынешних записей. В UI показывать текущую оценку, фактический объём и дату оценки; не смешивать «объём» и «часы».
- **US-34 Detect Problematic Activities (6):** флаг роста ставится только если есть **две сравнимые** оценки и новая оценка полного объёма выше предыдущей на согласованный порог. Рабочий стартовый порог: рост минимум на 20% при положительной предыдущей оценке; при нулевой предыдущей оценке рост показывать отдельно без деления на ноль. Флаг низкого прогресса требует известного планового срока и достаточных данных: прошло минимум 7 дней, не менее 75% планового периода, а выполнено менее 25% последней известной полной оценки. Пороги настраиваются на backend и возвращаются в ответе. Каждый флаг содержит причину и исходные числа. Если данных недостаточно, статус `INSUFFICIENT_DATA` — не «проблема».

**Граница кода:** V11 (snapshot для estimate), `ManagerProgress*` controller/service/DTO/repository, компоненты прогресса и рисков, тесты. D один владеет точечным изменением Sprint 3 weekly estimate save logic для записи snapshot. Не менять `ProjectManagerProject*`, staffing и Review. Данные D встраиваются в страницу проекта/активности через отдельный компонент; интегратор подключает маршрут/вкладку.

**API-контракт:** `GET /project-manager/projects/{projectId}/activities/{activityId}/progress` и `GET /project-manager/projects/{projectId}/risks`. Ответы явно различают `null`, ноль и `INSUFFICIENT_DATA`; агрегаты и флаги считаются на backend, а не в React.

**QA:** дневные записи двух переводчиков суммируются с понятной оговоркой, неизвестные часы/остаток не превращаются в ноль; snapshot оценки сохраняется при недельном обновлении; две оценки с ростом дают флаг, стабильная оценка — нет; низкий прогресс у близкой к сроку активности даёт флаг только при достаточной выборке; чужой менеджер не читает прогресс.

## 4. Общая приёмка и слияние

Каждый PR должен содержать свой backend и frontend, тесты своих серверных правил и React-сценариев, миграцию при изменении БД, короткую инструкцию ручной демонстрации и перечень изменённых общих файлов. Данные демо не должны обходить роль/квоты. Запустить `cd backend && mvn test`, `cd frontend && npm test`, `npm run lint`, `npm run build`; PostgreSQL/Flyway и E2E — на отдельной БД после запуска API и web. Если тест не запускался, указать причину; не писать «прошёл» без запуска.

Интегратор принимает PR только при работающем предыдущем контракте, собирает миграции в указанном порядке, подключает feature-страницы в `App.tsx`, обновляет API/архитектуру/дизайн, разрешает `STATE.md` без потери записей и запускает общий сценарий: создать проект → активность → назначить/заменить переводчика → увидеть доступность и нагрузку → внести работу/estimate → увидеть прогресс/риск → отправить на проверку → подключить дополнительного редактора → записать ошибки → увидеть показатель качества. Особое внимание — права доступа по ID, CSRF, старые строки после миграций и сохранность Sprint 2–4.

**Готовая команда для ИИ исполнителя:** «Прочитай `AGENTS.md`, `docs/STATE.md`, `docs/ARCHITECTURE.md`, этот файл, а для UI также `docs/DESIGN.md` и `$frontend-design`. Мой кейс — **[A/B/C/D]**. Реализуй только его истории и тесты в своей ветке от согласованного commit SHA. Следуй контракту и границам файлов; если общий контракт не готов или обнаружено противоречие, опиши точный блокер интегратору, не выдумывай несовместимую схему. В конце укажи изменённые файлы, миграцию, API, проверки и ручной QA; обнови `docs/STATE.md`».
